1Ściąga: pytania, które już padły

Lista z czatu: tematy, o które pytano na zaliczeniu. Najpierw spróbuj odpowiedzieć sam, potem rozwiń.

Co to jest przeładowanie funkcji (metody)?

Kilka metod o tej samej nazwie w jednej klasie, różniących się listą parametrów (liczbą, typem lub kolejnością). Sam typ zwracany nie wystarczy. Przykład: dodaj(int, int) i dodaj(double, double). Przeładowanie a nadpisanie

Czy metoda abstrakcyjna w klasie wymusza abstrakcyjność klasy?

Tak. W drugą stronę nie: klasa abstrakcyjna nie musi mieć żadnej metody abstrakcyjnej.

Jakim operatorem porównasz tożsamość obiektów?

Java, C#: == na referencjach (a equals() porównuje zawartość). Python: is. JavaScript, PHP: ===. Tożsamość a równość

Jakim symbolem w UML oznacza się kompozycję?

Linia ciągła z wypełnionym (czarnym) rombem po stronie całości. Pusty romb to agregacja. Wszystkie strzałki

Jak w UML zapisać metodę statyczną?

Podkreśleniem, np. + policz(x: int): int. Kursywa oznacza abstrakcyjność.

Wymień zasady SOLID

S jedna odpowiedzialność, O otwarte na rozszerzanie, zamknięte na modyfikację, L podstawienie Liskov, I segregacja interfejsów, D odwrócenie zależności. Tabela z przykładami

Pamiątka: co robi i jak ją narysować?

Zapisuje i przywraca stan (Cofnij) bez łamania hermetyzacji. Twórca tworzy i czyta Pamiątkę (przerywana ze strzałką), Opiekun przechowuje listę pamiątek (ciągła z pustym rombem). Diagram

Adapter: co robi i jak go narysować?

Tłumaczy jeden interfejs na inny. Adapter implementuje interfejs docelowy (przerywana z pustym trójkątem) i trzyma referencję do adaptowanego obiektu (ciągła ze strzałką). Diagram

Hermetyzacja w skrócie

Ukrycie stanu za metodami. Gdy do wszystkich pól dostaje się wyłącznie przez metody, to hermetyzacja pełna. Pełna wersja do odpowiedzi ustnej: filary OOP, hermetyzacja.

Tożsamość a równość

Pułapka: w Javie == na dwóch String z new daje false, chociaż tekst jest ten sam.

Tożsamość: dwie zmienne wskazują ten sam obiekt w pamięci. Równość: dwa różne obiekty mają tę samą zawartość.

String a = new String("ala");
String b = new String("ala");
a == b;        // false: dwa różne obiekty (tożsamość)
a.equals(b);   // true: ta sama zawartość (równość)
a == a;        // true

C#: == dla klas porównuje referencje, chyba że klasa przeciąża operator (jak string); pewne sprawdzenie tożsamości daje ReferenceEquals(a, b). C++: porównujesz adresy, &a == &b.

4Cztery filary programowania obiektowego

Abstrakcja, hermetyzacja, dziedziczenie, polimorfizm. Pod każdym filarem jest gotowa odpowiedź ustna: definicja, po co to jest, jak to wygląda w kodzie, przykład i typowe pytanie dodatkowe.

Abstrakcja nowe

Pokazujemy, co obiekt robi, a ukrywamy, jak to robi.

Odpowiedź ustna

Abstrakcja polega na wybraniu z rzeczywistego obiektu tylko tych cech i zachowań, które są ważne w danym problemie, i pominięciu reszty. Klasa Samochod w programie do wypożyczalni ma numer rejestracyjny i cenę za dobę, ale nie ma składu chemicznego lakieru. W kodzie abstrakcję wyrażamy klasami abstrakcyjnymi i interfejsami: określają kontrakt (jakie metody istnieją), nie mówiąc nic o implementacji. Dzięki temu kod korzystający z obiektu zależy od kontraktu, a nie od szczegółów, i szczegóły można zmieniać bez psucia reszty programu.

Różnica z hermetyzacją, o którą często pytają: abstrakcja dotyczy projektu (jaki interfejs pokazać światu), hermetyzacja dotyczy ochrony (jak schować dane, żeby nikt ich nie zepsuł). Abstrakcja odpowiada na pytanie „co”, hermetyzacja na pytanie „kto ma dostęp”.

Hermetyzacja (enkapsulacja)

Dane obiektu są prywatne, a zmieniać je można tylko przez metody, które pilnują poprawności.

Odpowiedź ustna

Hermetyzacja wiąże dane z metodami, które na nich operują, i ogranicza dostęp do stanu obiektu z zewnątrz. Realizuje się ją modyfikatorami dostępu: pola są prywatne (-), a publiczne (+) są tylko metody. Po co: obiekt sam pilnuje swoich niezmienników, czyli reguł, które zawsze muszą być prawdziwe, np. saldo konta nie może spaść poniżej zera. Gdyby pole saldo było publiczne, każdy mógłby wpisać tam dowolną liczbę. Druga korzyść: można zmienić wewnętrzną reprezentację (np. trzymać grosze zamiast złotych) bez zmiany kodu, który korzysta z klasy. Gdy wszystkie pola są dostępne tylko przez metody, mówimy o hermetyzacji pełnej.

Pułapka: getter i setter do każdego pola bez żadnej kontroli to tylko udawana hermetyzacja.
class Konto {
    private double saldo;                     // nikt z zewnątrz nie zmieni wprost

    public double getSaldo() { return saldo; }

    public void wplac(double kwota) {
        if (kwota <= 0) throw new IllegalArgumentException("Kwota musi być dodatnia");
        saldo += kwota;
    }
    public void wyplac(double kwota) {
        if (kwota > saldo) throw new IllegalStateException("Brak środków");
        saldo -= kwota;                       // niezmiennik: saldo >= 0
    }
}

Pytanie dodatkowe: czym różni się protected od private? Składnik chroniony widzą też klasy pochodne, prywatny tylko sama klasa. W Javie protected widzą dodatkowo klasy z tego samego pakietu.

Dziedziczenie

Klasa pochodna przejmuje cechy klasy bazowej i może je rozszerzać lub zmieniać.

Odpowiedź ustna

Dziedziczenie to relacja „jest rodzajem” (is-a): Student jest rodzajem Osoba. Klasa pochodna dziedziczy wszystkie pola i metody klasy bazowej, może dodawać własne i nadpisywać odziedziczone metody. Klasa bazowa jest uogólnieniem, pochodna specjalizacją. Zalety: ponowne użycie kodu i możliwość traktowania obiektów pochodnych jak bazowych, co jest podstawą polimorfizmu. Wady: silne powiązanie, bo zmiana w klasie bazowej wpływa na wszystkie pochodne, a dziedziczenie ustala się przy kompilacji i nie da się go zmienić w czasie działania programu. Dlatego przy relacji „ma” (has-a) lepiej użyć kompozycji. W Javie i C# klasa dziedziczy tylko po jednej klasie, ale może implementować wiele interfejsów; C++ pozwala na wielodziedziczenie. W UML: linia ciągła z pustym trójkątem przy klasie bazowej.

class Osoba {
    protected String imie;
    Osoba(String imie) { this.imie = imie; }
    String przedstawSie() { return "Jestem " + imie; }
}

class Student extends Osoba {
    private int album;
    Student(String imie, int album) {
        super(imie);                          // najpierw konstruktor klasy bazowej
        this.album = album;
    }
    @Override
    String przedstawSie() {                   // nadpisanie
        return super.przedstawSie() + ", nr albumu " + album;
    }
}
Kolejność: przy tworzeniu obiektu najpierw działa konstruktor klasy bazowej, potem pochodnej.

Pytania dodatkowe: co to jest super? Odwołanie do klasy bazowej: wywołanie jej konstruktora albo jej wersji metody. Czy dziedziczy się składniki prywatne? Są w obiekcie, ale klasa pochodna nie ma do nich bezpośredniego dostępu. Czy dziedziczy się konstruktory? Nie, każda klasa ma własne i musi wywołać konstruktor bazowy.

Polimorfizm

Jedno wywołanie, różne zachowanie, zależnie od faktycznego typu obiektu.

Odpowiedź ustna

Polimorfizm (wielopostaciowość) to mechanizm, który pozwala korzystać z jednego interfejsu obiektom różnych typów. Zmienna typu bazowego Figura może wskazywać na Kolo albo Kwadrat, a wywołanie f.pole() uruchomi wersję z klasy faktycznego obiektu. Rozróżniamy dwa rodzaje. Polimorfizm dynamiczny (czasu wykonania) opiera się na nadpisywaniu metod wirtualnych; decyzja, która wersja się wykona, zapada w czasie działania programu (późne wiązanie, w C++ przez tablicę metod wirtualnych). Polimorfizm statyczny (czasu kompilacji) to przeładowanie metod i operatorów oraz szablony i typy generyczne; wersję wybiera kompilator na podstawie typów argumentów. Po co: kod pisany względem typu bazowego działa z każdą nową klasą pochodną bez zmian, co realizuje zasadę otwarte/zamknięte.

abstract class Figura { abstract double pole(); }
class Kolo    extends Figura { double r; Kolo(double r) { this.r = r; }    double pole() { return Math.PI * r * r; } }
class Kwadrat extends Figura { double a; Kwadrat(double a) { this.a = a; } double pole() { return a * a; } }

List<Figura> figury = List.of(new Kolo(1), new Kwadrat(2));
for (Figura f : figury) {
    System.out.println(f.pole());   // 3.14..., potem 4.0: ta sama linia, różne metody
}

Rzutowanie w górę i w dół

Upcasting (Figura f = new Kolo(1);) jest zawsze bezpieczny i niejawny. Downcasting (Kolo k = (Kolo) f;) wymaga jawnego rzutowania i może rzucić ClassCastException, więc sprawdza się go przez instanceof. Częste używanie downcastingu sugeruje źle zaprojektowany polimorfizm.

Pytanie dodatkowe: czy metodę statyczną można wywołać polimorficznie? Nie. Metody statyczne są wiązane przy kompilacji według typu zmiennej; w klasie pochodnej można je tylko przesłonić (ukryć), nie nadpisać.

5Inne pojęcia, o które mogą zapytać nowe

Konstruktor i destruktor
Konstruktor ustawia stan początkowy obiektu, można go przeładować (kilka wersji z różnymi parametrami). Konstruktor domyślny (bezargumentowy) kompilator tworzy sam, tylko gdy nie napiszesz żadnego. Destruktor (C++: ~Klasa()) sprząta przy niszczeniu obiektu; w Javie i C# pamięć zwalnia garbage collector, więc destruktorów w tym sensie nie piszemy.
this
Referencja do bieżącego obiektu. Używana do odróżnienia pola od parametru (this.imie = imie) i do wywołania innego konstruktora tej samej klasy. Nie istnieje w metodach statycznych.
Pole statyczne a pole instancyjne
Pole instancyjne ma osobną wartość w każdym obiekcie. Pole statyczne istnieje raz dla całej klasy i jest wspólne dla wszystkich obiektów, np. licznik utworzonych obiektów. W UML podkreślone.
Kompozycja zamiast dziedziczenia
Zasada: gdy relacja to „ma” (Samochód ma Silnik), trzymaj obiekt w polu zamiast po nim dziedziczyć. Kompozycję można zmieniać w czasie działania (podmienić obiekt), dziedziczenie jest ustalone przy kompilacji. Na tym opierają się Dekorator, Strategia i Stan.
Wielodziedziczenie i problem diamentu
Klasa D dziedziczy po B i C, które obie dziedziczą po A. Jeśli B i C nadpisały tę samą metodę A, nie wiadomo, którą wersję ma D. C++ rozwiązuje to dziedziczeniem wirtualnym; Java i C# po prostu nie pozwalają dziedziczyć po wielu klasach, tylko implementować wiele interfejsów.
Wiązanie wczesne i późne
Wczesne (statyczne): wersja metody znana przy kompilacji, np. metody statyczne, prywatne, finalne, przeładowane. Późne (dynamiczne): wybierana w czasie działania według faktycznego typu obiektu, np. metody wirtualne. Późne wiązanie umożliwia polimorfizm dynamiczny.
Kopia płytka i głęboka
Płytka kopiuje pola, ale referencje dalej wskazują te same obiekty w środku, więc zmiana w jednym wpływa na drugi. Głęboka kopiuje także obiekty wskazywane. Ważne np. przy Pamiątce: migawka musi być niezależna od oryginału.
Spójność (cohesion) i powiązanie (coupling)
Dobry projekt ma wysoką spójność (klasa robi jedną, dobrze określoną rzecz, por. zasada S) i niskie powiązanie (klasy mało wiedzą o sobie nawzajem, por. zasada D). Wzorce projektowe w większości służą obniżeniu powiązania.
Klasa finalna
final class (Java) lub sealed class (C#) nie może mieć klas pochodnych. Przykład: String w Javie. Często używana razem z niemodyfikowalnymi obiektami.
Obiekt niemodyfikowalny (immutable)
Po utworzeniu jego stanu nie da się zmienić: pola final, brak setterów. Bezpieczny przy współbieżności i jako klucz w mapie. Pamiątka powinna być niemodyfikowalna.
Wyjątki a hermetyzacja
Metoda, która dostaje błędne dane, rzuca wyjątek (np. IllegalArgumentException) zamiast po cichu ustawić zły stan. To sposób, w jaki obiekt broni swoich niezmienników; w Lab 1 wymagane jest blokowanie błędnych danych od użytkownika.

6Rodzaje metod

Metody dzieli się według tego, do czego należą (klasa czy obiekt) i jak zachowują się przy dziedziczeniu.

Instancyjna (zwykła)
Należy do obiektu, trzeba go najpierw utworzyć: auto.jedz(). Widzi pola i stan obiektu.
Statyczna static
Należy do klasy, wołasz ją bez obiektu: Math.sqrt(9). Nie widzi zwykłych pól obiektu. W UML: podkreślenie.
Abstrakcyjna abstract
Sama sygnatura, bez ciała. Tylko w klasie abstrakcyjnej; klasy pochodne muszą ją dopisać. W UML: kursywa.
Wirtualna virtual / nadpisana override
Ma domyślny kod w klasie bazowej, klasa pochodna może go zmienić. W Javie każda zwykła metoda jest domyślnie wirtualna.
Finalna final / zapieczętowana sealed
Zablokowana: klasa pochodna nie może jej nadpisać.
Konstruktor
Nazwa jak klasa, uruchamia się przy tworzeniu obiektu i ustawia wartości początkowe.

Pokaż wszystkie rodzaje w jednej klasie (Java) 
abstract class Figura {
    private static int licznik = 0;            // pole statyczne: jedno na całą klasę
    protected String nazwa;

    Figura(String nazwa) {                     // konstruktor
        this.nazwa = nazwa;
        licznik++;
    }
    static int ileFigur() { return licznik; }  // statyczna: Figura.ileFigur()
    abstract double pole();                    // abstrakcyjna: brak ciała
    String opis() { return nazwa + ": " + pole(); }  // instancyjna (wirtualna)
    final String id() { return nazwa.toUpperCase(); } // finalna
}

class Kolo extends Figura {
    private final double r;
    Kolo(double r) { super("koło"); this.r = r; }
    @Override
    double pole() { return Math.PI * r * r; }   // nadpisanie metody abstrakcyjnej
}

7Relacje i strzałki UML

Na diagramie klas wystarczą prostokąty i sześć rodzajów linii. Kolejność poniżej to kolejność według siły relacji z Lab 1, od najsilniejszej.

  1. Dziedziczenie

    Przekazanie wszystkich cech. Klasa pochodna jest szczególnym przypadkiem bazowej.

    Linia ciągła, pusty trójkąt przy klasie bazowej. Czasem z dopiskiem Extends.

  2. Implementacja interfejsu

    Klasa realizuje kontrakt interfejsu. Nie ma jej na liście z Lab 1, ale rysuje się ją w każdym wzorcu.

    Linia przerywana, pusty trójkąt przy interfejsie.

  3. Kompozycja (agregacja całkowita)

    Całość tworzy części i nimi zarządza. Żyją tyle samo: usunięcie domu usuwa pokoje.

    Linia ciągła, wypełniony romb przy całości.

  4. Agregacja częściowa

    Całość zawiera części, ale nimi nie zarządza. Po likwidacji firmy osoby dalej istnieją.

    Linia ciągła, pusty romb przy całości.

  5. Asocjacja

    Czasowe powiązanie niezależnych obiektów. Nikt nikogo nie tworzy ani nie usuwa. Zwykle ma nazwę-czasownik.

    Linia ciągła; otwarta strzałka, gdy chcesz pokazać kierunek „kto kogo wywołuje”.

  6. Zależność

    Jedna klasa oddziałuje na drugą, np. tworzy jej obiekt albo bierze go w parametrze.

    Linia przerywana z otwartą strzałką, często ze stereotypem «create».

Krotności nowe

Romb zawsze stoi przy całości, a trójkąt przy klasie ogólniejszej. Na odwrót to najczęstszy błąd.

Liczby przy końcach linii mówią, ile obiektów bierze udział w relacji: 1 dokładnie jeden, 0..1 zero lub jeden, 0..* lub * dowolnie wiele, 1..* co najmniej jeden, n dokładnie n. Na rysunku asocjacji: jedna osoba akceptuje od zera do n umów.

Singleton kreacyjny nowe

Ogranicza liczbę obiektów klasy do jednego i daje do niego globalny dostęp.

Odpowiedź ustna

Singleton to wzorzec kreacyjny, który gwarantuje, że klasa ma dokładnie jeden obiekt, i daje do niego globalny punkt dostępu. Konstruktor jest prywatny, więc nikt z zewnątrz nie zrobi new. Klasa trzyma swoją jedyną instancję w statycznym polu i udostępnia statyczną metodę getInstance(): przy pierwszym wywołaniu tworzy obiekt (leniwa inicjalizacja), przy kolejnych zwraca ten sam. Stosuje się go do zasobów, które muszą być jedne, np. konfiguracja, połączenie z bazą, logger. Wady: to w praktyce zmienna globalna, utrudnia testowanie i ukrywa zależności, a w programach wielowątkowych trzeba zsynchronizować tworzenie.

Trzy elementy: prywatny konstruktor, statyczne pole z instancją (na początku null) i statyczna metoda getInstance(), która zwraca instancję, a jeśli jej nie ma, wywołuje konstruktor i zapamiętuje wynik.

Pułapka: bez synchronized dwa wątki mogą naraz zobaczyć null i utworzyć dwa obiekty.
Kod (Java) 
public final class Konfiguracja {
    private static Konfiguracja instance = null;   // statyczne pole
    private Konfiguracja() { }                     // prywatny konstruktor

    public static synchronized Konfiguracja getInstance() {
        if (instance == null) {
            instance = new Konfiguracja();
        }
        return instance;
    }
}

Konfiguracja a = Konfiguracja.getInstance();
Konfiguracja b = Konfiguracja.getInstance();
// a == b  ->  true, to ten sam obiekt

Adapter strukturalny

Łączy dwie niepasujące klasy: tłumaczy interfejs, którego oczekuje klient, na interfejs istniejącej klasy, bez ruszania jej kodu.

Odpowiedź ustna

Adapter to wzorzec strukturalny, który pozwala współpracować klasom o niezgodnych interfejsach bez zmiany ich kodu. Mamy klienta, który oczekuje interfejsu docelowego (Target), i istniejącą klasę (Adaptee) z innym interfejsem. Adapter implementuje interfejs docelowy, a w środku trzyma referencję do obiektu adaptowanego i tłumaczy wywołania: zamienia nazwy metod, przelicza dane, zmienia format. Klient rozmawia tylko z adapterem. W Lab 2 Polar2DAdapter implementuje IPolar2D, deleguje abs(), cdot() i getComponents() do Vector2D, a jedyną nową logiką jest getAngle() liczone przez atan2. Przewaga nad dziedziczeniem: adapter działa na istniejącym obiekcie w czasie działania programu i nie wiąże się z konkretną podklasą.

Jak przejściówka do gniazdka albo nakładka, która z XML starej biblioteki robi JSON dla nowego systemu. Poniżej wersja z Lab 2: klient chce kąt wektora w układzie biegunowym, a Vector2D zna tylko x i y.

Jak narysować adapter: adapter implementuje interfejs docelowy (przerywana linia, pusty trójkąt) i trzyma referencję do obiektu adaptowanego (ciągła linia ze strzałką). Wszystkie metody poza nową deleguje do srcVector.

Lab 2 pokazuje też wersję z dziedziczeniem (2DPolarInheritance extends Vector2D). Wada: działa tylko przy kompilacji, nie zaadaptujesz istniejącego obiektu.
Kod (Java) 
interface IVector  { double abs(); double cdot(IVector p); double[] getComponents(); }
interface IPolar2D { double getAngle(); }

class Polar2DAdapter implements IVector, IPolar2D {
    private final Vector2D srcVector;
    Polar2DAdapter(Vector2D v) { this.srcVector = v; }

    public double abs()               { return srcVector.abs(); }        // delegacja
    public double cdot(IVector p)     { return srcVector.cdot(p); }
    public double[] getComponents()   { return srcVector.getComponents(); }

    public double getAngle() {                                           // jedyna nowa logika
        double[] c = srcVector.getComponents();
        return Math.atan2(c[1], c[0]);
    }
}

Dekorator strukturalny

Dynamicznie dokłada obiektowi nowe zachowanie, bez zmiany jego kodu i bez mnożenia podklas.

Odpowiedź ustna

Dekorator to wzorzec strukturalny do dynamicznego dodawania obiektom nowych funkcji. Dekorator implementuje ten sam interfejs co obiekt dekorowany i jednocześnie przechowuje do niego referencję. Każde wywołanie przekazuje dalej do obiektu w środku, a przed albo po nim dokłada własne zachowanie. Ponieważ interfejs się nie zmienia, dekoratory można nakładać jeden na drugi w dowolnej kolejności. Rozwiązuje to problem eksplozji podklas: zamiast klasy na każdą kombinację dodatków mamy jedną klasę na każdy dodatek. W Lab 2 Vector3DDecorator owija dowolny IVector, dodaje składową z i metodę cross(), a getSrcV() oddaje oryginał. Wersja z dziedziczeniem (Vector3DInheritance) musi utworzyć nowy obiekt i jest ustalona przy kompilacji.

Zamiast klas KawaZMlekiem, KawaZSyropem, KawaZMlekiemISyropem owijasz KawaBaza w dekorator Mleko, a potem w Syrop. Każdy woła cena() obiektu w środku i dolicza swoją kwotę. W Lab 2 dekorator dodaje wektorowi trzeci wymiar i iloczyn wektorowy.

Jak rozpoznać dekorator na diagramie: klasa implementuje interfejs i jednocześnie go zawiera (dwie linie do tego samego interfejsu: trójkąt i romb).

Kod (Java), iloczyn wektorowy metodą macierzową 
class Vector3DDecorator implements IVector {
    private final IVector srcVector;   // owinięty obiekt
    private final double z;

    Vector3DDecorator(IVector v, double z) { this.srcVector = v; this.z = z; }

    public double[] getComponents() {
        double[] c = srcVector.getComponents();
        return new double[] { c[0], c[1], z };
    }
    public double abs() {
        double[] c = getComponents();
        return Math.sqrt(c[0]*c[0] + c[1]*c[1] + c[2]*c[2]);
    }
    public double cdot(IVector p) {
        double[] a = getComponents(), b = p.getComponents();
        double bz = b.length > 2 ? b[2] : 0;          // wektor 2D ma z = 0
        return a[0]*b[0] + a[1]*b[1] + a[2]*bz;
    }
    public Vector3DDecorator cross(IVector p) {
        double[] a = getComponents(), b = p.getComponents();
        double bz = b.length > 2 ? b[2] : 0;
        double x = a[1]*bz   - a[2]*b[1];
        double y = a[2]*b[0] - a[0]*bz;
        double zz = a[0]*b[1] - a[1]*b[0];
        return new Vector3DDecorator(new Vector2D(x, y), zz);
    }
    public IVector getSrcV() { return srcVector; }
}

Stan behawioralny

Obiekt zmienia zachowanie zależnie od stanu, w którym jest. Z zewnątrz wygląda, jakby zmienił klasę.

Odpowiedź ustna

Stan to wzorzec behawioralny, w którym obiekt zmienia zachowanie, gdy zmienia się jego stan wewnętrzny. Zamiast jednej klasy z rozbudowanymi instrukcjami if albo switch po polu „stan”, każdy stan jest osobną klasą implementującą wspólny interfejs. Kontekst przechowuje referencję do bieżącego obiektu stanu i deleguje mu wywołania, przekazując siebie w parametrze. Konkretne stany decydują, co zrobić, i same przełączają kontekst w następny stan. Odpowiada to automatowi skończonemu. Zalety: nowy stan to nowa klasa (zasada otwarte/zamknięte), logika jednego stanu jest w jednym miejscu (zasada jednej odpowiedzialności). Wada: więcej klas przy małej liczbie stanów.

Przykład z diagramu: ta sama metoda anuluj() w stanie Nowe zwraca pieniądze, a w stanie Wysłane blokuje operację. Inne przykłady: automat z napojami, stan wozu w Lab 4 (wolny, zajęty).

Kod (Java) 
interface StanZamowienia {
    void oplac(Zamowienie z);
    void anuluj(Zamowienie z);
}

class StanNowe implements StanZamowienia {
    public void oplac(Zamowienie z)  { z.zmienStan(new StanWyslane()); }
    public void anuluj(Zamowienie z) { System.out.println("Anulowano, zwrot pieniędzy"); }
}

class StanWyslane implements StanZamowienia {
    public void oplac(Zamowienie z)  { System.out.println("Już opłacone"); }
    public void anuluj(Zamowienie z) { System.out.println("Nie można anulować wysłanego"); }
}

class Zamowienie {
    private StanZamowienia stan = new StanNowe();
    void zmienStan(StanZamowienia s) { stan = s; }
    void oplac()  { stan.oplac(this); }      // delegacja, bez if/switch
    void anuluj() { stan.anuluj(this); }
}

Pamiątka (Memento) behawioralny

Zapisuje migawkę stanu obiektu i pozwala go później przywrócić (Cofnij, zapis gry), nie ujawniając prywatnych pól.

Odpowiedź ustna

Pamiątka (Memento) to wzorzec behawioralny, który pozwala zapisać i później przywrócić stan obiektu bez naruszania hermetyzacji. Ma trzy role. Twórca to obiekt, którego stan zapisujemy; sam tworzy pamiątkę ze swoich prywatnych pól i sam umie się z niej odtworzyć. Pamiątka to mały, niemodyfikowalny obiekt z migawką stanu. Opiekun przechowuje pamiątki, na przykład na stosie dla funkcji Cofnij, ale nie czyta ani nie zmienia ich zawartości; wie tylko, kiedy poprosić Twórcę o zapis lub przywrócenie. Dzięki temu nie trzeba upubliczniać pól Twórcy. Przykłady: Ctrl+Z w edytorze, zapis gry, w Lab 3 zapis i wczytanie symulacji w chwili t. Wada: przy dużym stanie i częstych zapisach zużycie pamięci.

Pytanie kontrolne: dlaczego Opiekun nie czyta pamiątki? Bo wtedy stan Twórcy wyciekałby na zewnątrz: koniec hermetyzacji.
Kod (Java) 
final class Pamiatka {
    private final String zapisanyTekst;
    Pamiatka(String t) { zapisanyTekst = t; }
    String pobierzTekst() { return zapisanyTekst; }
}

class EdytorTekstu {                       // Twórca
    private String tekst = "";
    void wpisz(String t) { tekst += t; }
    Pamiatka zapisz() { return new Pamiatka(tekst); }
    void przywroc(Pamiatka p) { tekst = p.pobierzTekst(); }
}

class Historia {                           // Opiekun
    private final Deque<Pamiatka> stos = new ArrayDeque<>();
    void dodaj(Pamiatka p) { stos.push(p); }
    Pamiatka cofnij() { return stos.pop(); }
}

// użycie: Ctrl+Z
historia.dodaj(edytor.zapisz());
edytor.wpisz(" coś nowego");
edytor.przywroc(historia.cofnij());

Strategia behawioralny nowe

Rodzina wymiennych algorytmów: każdy w osobnej klasie, wszystkie z tym samym interfejsem.

Klient tworzy obiekt strategii i wiąże go z kontekstem. Gdy klient prosi o akcję, kontekst deleguje ją do strategii. Nowy algorytm to nowa klasa, bez zmian w kontekście.

Kod (Java) 
interface IStrategy { void execute(); }

class NajblizszaJednostka implements IStrategy {
    public void execute() { System.out.println("Wysyłam z najbliższej JRG"); }
}
class KolejnaNajblizsza implements IStrategy {
    public void execute() { System.out.println("Brak wolnych wozów, szukam dalej"); }
}

class Context {
    private IStrategy strategy;
    void setStrategy(IStrategy s) { strategy = s; }
    void execute() { strategy.execute(); }       // delegacja
}

Context c = new Context();
c.setStrategy(new NajblizszaJednostka());
c.execute();

Iterator behawioralny nowe

Sekwencyjny dostęp do elementów kolekcji bez ujawniania jej wewnętrznej struktury.

Kolekcja ma metodę tworzącą iterator. Iterator ma hasNext() (czy są jeszcze elementy) i next() (daj kolejny). Pętla for (x : lista) w Javie to właśnie iterator pod spodem.

Kod (Java) 
interface Iterator  { boolean hasNext(); Object next(); }
interface Aggregate { Iterator iterator(); }

class ListaJednostek implements Aggregate {
    private final Object[] items;
    ListaJednostek(Object[] items) { this.items = items; }
    public Iterator iterator() { return new ListaIterator(this); }   // «create»
    int size() { return items.length; }
    Object get(int i) { return items[i]; }
}

class ListaIterator implements Iterator {
    private final ListaJednostek aggregate;
    private int index = 0;
    ListaIterator(ListaJednostek a) { aggregate = a; }
    public boolean hasNext() { return index < aggregate.size(); }
    public Object next() { return aggregate.get(index++); }
}

Iterator it = lista.iterator();
while (it.hasNext()) System.out.println(it.next());

Obserwator behawioralny nowe

Komunikacja jeden do wielu w formie subskrypcji: podmiot powiadamia wszystkich zapisanych obserwatorów o zmianie stanu.

Podmiot ma kolekcję obserwatorów i metody: dodaj, usuń, powiadom jednego, powiadom wszystkich. Obserwator ma jedną metodę update().

Pułapka w Javie: metody notifyAll() z diagramu nie napiszesz, bo Object.notifyAll() jest finalna. Nazwij ją np. notifyAllObservers().
Kod (Java) 
interface Observer { void update(byte[] data); }

class ObservedSubject {
    private final List<Observer> observers = new ArrayList<>();
    protected byte[] state;

    public void addObserver(Observer o)    { observers.add(o); }
    public void removeObserver(Observer o) { observers.remove(o); }
    public void notifyObserver(Observer o) { o.update(state); }
    public void notifyAllObservers() {
        for (Observer o : observers) o.update(state);
    }
}

class JednostkaJRG implements Observer {
    public void update(byte[] data) { System.out.println("Nowe zgłoszenie"); }
}

10Wektory i układy współrzędnych

Z Lab 2: wektor wodzący zaczyna się w (0, 0). W układzie kartezjańskim zapisujesz go jako (x, y), w biegunowym jako (r, α): długość i kąt od osi OX.

Biegunowy → kartezjański

x = r · cos α
y = r · sin α

Kartezjański → biegunowy

r = √(x² + y²)
α = atan2(y, x)

Ręcznie: α = arctan(y / x) dla x > 0, dla x < 0 dodaj π (180°).

Moduł i iloczyn skalarny nowe

|a| = √(x² + y² + z²)
a · b = x₁x₂ + y₁y₂ + z₁z₂

Wynik iloczynu skalarnego to liczba.

Iloczyn wektorowy nowe

        | i   j   k  |
a × b = | x₁  y₁  z₁ |
        | x₂  y₂  z₂ |

x: y₁z₂ − z₁y₂
y: z₁x₂ − x₁z₂
z: x₁y₂ − y₁x₂

Wynik to wektor prostopadły do a i b. Dla wektorów 2D przyjmij z = 0, wtedy wychodzi (0, 0, x₁y₂ − y₁x₂).

Policz i sprawdź się

Kartezjański → biegunowy

Wpisz x i y, wynik pojawi się tutaj.

Biegunowy → kartezjański

Wpisz r i kąt, wynik pojawi się tutaj.

Iloczyn skalarny i wektorowy

Wpisz składowe obu wektorów (dla 2D zostaw z = 0). Wynik z rozpisanymi krokami pojawi się tutaj.
